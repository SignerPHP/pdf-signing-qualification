# Result schemas

Machine-readable contracts written and read by every stage, as JSON Schema draft 2020-12 (RFC sections 6.3, 6.4, 6.6 and 7).

| Schema | Describes |
| ------ | --------- |
| [`v2/sources.schema.json`](v2/sources.schema.json) | Upstream sources pinned at a revision, the inputs selected from them with their strata, and how they were selected |
| [`v1/sources.schema.json`](v1/sources.schema.json) | The previous version, without strata or selection, kept for the configurations of earlier revisions; nothing reads it now |
| [`v1/panel-selection.schema.json`](v1/panel-selection.schema.json) | How a stratified panel is drawn: the pinned sources that form its pool, the files and sources left out with their reasons, the seed and the quota per stratum |
| [`v1/panel-pool.schema.json`](v1/panel-pool.schema.json) | The pool a stratified panel was drawn from: its candidates and drawn inputs per source and stratum, the files each exclusion left out, and the files that could not be candidates |
| [`v1/acquisition.schema.json`](v1/acquisition.schema.json) | The outcome of acquiring one declared input: its provenance and licenses, or why it is unavailable |
| [`v1/scenario.schema.json`](v1/scenario.schema.json) | An explicit operation configuration, including digest and signature algorithms |
| [`v1/expected-rejections.schema.json`](v1/expected-rejections.schema.json) | The inputs expected to be rejected under a scenario, each with its reason |
| [`v1/regression.schema.json`](v1/regression.schema.json) | A reported defect as a replayable case: its originating issue, scenario, input and condition |
| [`v1/run.schema.json`](v1/run.schema.json) | One run of a scenario by one implementation over every declared input, with its environment and exact revisions |
| [`v1/attempt.schema.json`](v1/attempt.schema.json) | One execution of a scenario by one implementation on one input |
| [`v1/observation.schema.json`](v1/observation.schema.json) | One analyzer's verdict on one property of an attempt's output |
| [`v1/baseline.schema.json`](v1/baseline.schema.json) | One analyzer's verdict on one property of an available input, before signing |
| [`v1/regressions.schema.json`](v1/regressions.schema.json) | The regression cases replayed by one run, and whether the condition of each is present in its output |
| [`v1/comparison.schema.json`](v1/comparison.schema.json) | What changed between a reference run and a candidate run, per input and scenario and per regression case |
| [`v1/differential.schema.json`](v1/differential.schema.json) | Two runs of each of two implementations over the same inputs: the denominator of every run and each capability, execution outcome and verdict classified with its evidence |
| [`v1/measurement.schema.json`](v1/measurement.schema.json) | Resource usage of one attempt within a declared boundary |
| [`v1/common.schema.json`](v1/common.schema.json) | Shared definitions: hashes, artifacts, revisions, verdicts, metrics |

## Versioning

Every document carries a `schema` field equal to the `$id` of the schema it follows, so readers never guess the version. A change that makes a previously valid document invalid, or changes the meaning of a field, goes into a new directory (`v2/`) and leaves the previous version in place.

## Semantics

- **Sources.** A source is an upstream project at an immutable revision, with a `file_url` template in which `{revision}` and `{path}` are replaced to download one file. An input names its source, its path inside it, the SHA-256 and byte size it must have, the document's own license and its strata. Its identity is `<source>:<path>`, the `source_id` used by attempts.
- **Strata and selection.** Version 2 of the sources schema requires both, which made every version 1 configuration invalid, so they are in `v2/` and `v1/` is unchanged. Every input lists at least one stratum, without repeats, from the closed list in the schema: `classic`, `stream`, `hybrid`, `none`, `objstm`, `encrypted`, `incremental`, `signed`, `malformed`, `forms`, `legacy`, `large`, `timestamped` and `revocation`, each described there. Strata overlap, so an input usually has several. The configuration also declares how its inputs were selected: `failure_enriched` when they were chosen for the defects and edge cases they hold, so a rate over them is not a compatibility rate; `stratified` when they were drawn from a stated pool by a quota per stratum, so a rate holds for one stratum of that pool only; or `representative` when they were chosen to stand for the documents found in practice. The values and strata added after version 2 was first written leave every earlier configuration valid, so they stay in `v2/`. A new stratum is added to the schema before an input uses it.
- **License.** An SPDX expression, or `NOASSERTION` when the evidence does not establish one, always with the URL of that evidence. The source project's license and the document's license are recorded separately, because a repository's license does not establish the license of each file in it.
- **Acquisition.** An available input records its retrieval time in UTC, its SHA-256 and byte size, and both licenses. A missing upstream file (HTTP 404 or 410) or a file whose hash or size differs from the declaration is recorded as `unavailable`, with the observed hash and size for a mismatch, and nothing is kept in the cache under its identity. Any other failure, such as an unreachable host, a server error, a timeout or a body shorter than its `Content-Length`, stops the acquisition instead of being recorded as missing.
- **Panel selection.** A selection plan names pinned sources, each with the URL of its recursive file listing, the license of its documents with the evidence for them, shell patterns of the files that are candidates and the exclusions, each with its reason; it also lists the sources rejected outright, the seed, the quota per stratum and the thresholds of `large`. `bin/select-panel` downloads every candidate, refuses a file whose bytes do not match the Git object id of the listing, records its strata with qpdf, draws candidates in the order of the SHA-256 of `<seed>:<source>:<path>` while one of their strata is below the quota, and writes the source configuration with `selection: stratified` and the pool next to it. Only regular files of the listing are considered, never symbolic links. A file whose path the sources schema cannot express as an input path is counted per source as unaddressable, a file the classifier gives no stratum as unclassified, and a file on which qpdf crashes, does not finish or ends with an unknown status is listed as an analyzer failure with its reason; none of them is drawn. `inputs.json` and `pool.json` are both written before either replaces the previous one. The pool records the SHA-256 of the plan and the qpdf version, so a reader can tell whether a configuration still matches its plan.
- **Run.** A run records the scenario, the operating system, PHP version and container image id it ran in, the limits applied to each attempt, the exact revision of the implementation and of every analyzer, and the SHA-256 and size of the source configuration and of the expected rejections. The runner reads the source configuration once, records the SHA-256 and size of those bytes, and writes the same bytes into the run directory as `inputs.json` with the other records, just before `run.json`, so the run directory alone tells the strata of each input. A run that stops earlier leaves no `inputs.json`, and the configuration may be the `inputs.json` of the same directory. The image id is passed by `bin/pilot`, because a container cannot read it; when it is missing it is recorded as `unavailable` with its reason, never guessed. `resource_limits` and `expected_rejections` are optional in the schema because older runs do not have them, and the current runner always writes them. `implementation_runtime` is what the implementation itself reports beyond its revision, such as its Java version and options, environment variables, engine and wrapper revision; an implementation with nothing to report has none. `implementation_compatibility` says whether the adapter's command applies to the installed revision, checked once before any attempt: `compatible`, `incompatible` with the reason, or `not_checked` for an adapter without a check. It is optional in the schema because older runs do not have it. A run has exactly one acquisition record per declared input and produces one attempt per input, one observation per attempt and analyzer and one baseline per available input and analyzer that judges one document, so nothing is skipped; it stops before signing if a record is missing, duplicated, undeclared or for another hash.
- **Attempt.** `capability` (`supported`, `unsupported`, `expected_rejection`, `not_evaluated`) is what was expected of the implementation for this scenario and input; `execution.outcome` (`succeeded`, `failed`, `timed_out`, `not_run`) is what happened. They are recorded independently: a rejection that was expected is a failed execution that the capability keeps from being read as a defect, and an expected rejection that succeeded is kept as an observed result, not rewritten.
- **Expected rejection.** `config/expected-rejections.json` declares, per input and scenario, that an implementation is expected to reject the input, with the reason. The declaration names the `source_id` of an input and the id of a scenario; the run stops before signing if it names an undeclared input or scenario, or repeats a pair. An attempt that runs on a declared pair has capability `expected_rejection`, and every other attempt that runs stays `supported`; an unavailable input stays `not_evaluated` and an unsupported scenario stays `unsupported`. An attempt counts as rejected only when the implementation ended by itself with a non-zero exit code; the summary totals those attempts apart from the outcomes and lists them apart from the failures. A declared attempt that timed out, was terminated by a signal, exited with 0 without a valid output or succeeded did not reject the input: it keeps its capability, the summary counts it under its outcome and keeps it under `Failures`, and the output of one that succeeded is validated like any other. A crash that a wrapper turns into a non-zero exit code cannot be told apart from a rejection. Declarations carry no password: an input that needs one is not declared for that reason alone. Declarations apply to every implementation, because the expectation comes from the input and the scenario.
- **Execution.** A succeeded execution has exit code 0, no error and an output. A failed or timed out execution carries its error message and both timestamps. A `not_run` attempt has no exit code, timestamps, error or output, and is only allowed when the input is unavailable or the capability is `unsupported`; an attempt that started is never recorded as `not_run`.
- **Unavailable input.** A missing upstream file or a hash mismatch is recorded as `input.status: unavailable` with its reason; a mismatch also records the observed hash. Such an attempt is `not_run` with capability `not_evaluated` and no output, so it can never be counted as an implementation failure. `not_evaluated` is used for no other case.
- **Revision.** Implementations and analyzers are identified by a full commit hash or a released version. Branch names and moving labels such as `latest` are rejected.
- **Identifier.** Identifiers may be split into `/` segments; each segment starts with a letter or digit, so `.`, `..` and empty segments are rejected. Input paths, and the identifiers that carry an input's `<source>:<path>` (the `source_id`, and the ids of attempts, observations and measurements), also keep a space inside a segment, because upstream paths such as veraPDF's contain them; a segment still cannot end with a space. Run, scenario, implementation, analyzer and policy identifiers never contain a space.
- **Verdict.** `valid`, `invalid` and `inconclusive` are judgements about an output artifact and require both the input and the output artifact. `not_evaluated` means the analyzer did not judge it (for example, the input was unavailable or no output was produced), and the missing artifact is recorded as `null`; `not_applicable` means the property does not apply to the scenario or to the input, such as the prior signatures of an unsigned input. Each analyzer writes its own observation; there is no combined verdict.
- **Baseline.** Before signing an input, the run gives it to every analyzer that judges one document, under the same policy used for the outputs, and writes one record per analyzer. An analyzer that compares the output with its input has nothing to judge before signing, so it has no baseline, and the summary names it. A baseline belongs to the run and the input, so it has no attempt and no output, and it needs a schema of its own: the observation schema requires both. It exists for every available input, whatever the implementation or scenario support; an unavailable input has none, and the summary lists it with its reason. The run refuses an input whose hash or size differs from its acquisition record before judging it. The verdicts mean what they mean for an output, with one exception: an input where a `cms_signature` analyzer finds no signature is `not_applicable`, because being unsigned is not a problem of an input, while the same finding on an output stays `invalid`. That finding only counts when the tool read the document: pyHanko has to finish with exit 0, `pdfsig` must not report a syntax or internal error, and qpdf must list the objects for `openssl-cms` with exit 0. Otherwise the baseline is `inconclusive`, because damage can hide a signature: a signed file that qpdf has to recover can lose its `/ByteRange` from the listing. `not_applicable` is only allowed for `cms_signature`, and `not_evaluated` is not a baseline verdict. `not_applicable` means that this analyzer found no signature, not that the document has none: each analyzer decides by itself, so they can disagree, and `pdfsig` can miss a signature in a damaged file without reporting an error. pyHanko reports none on veraPDF `6-1-12-t01-pass-a`, where `pdfsig` and `openssl-cms` find one. An empty signature form field is `inconclusive` for `pdfsig` and `not_applicable` for the other two. The summary shows each baseline next to the verdict on the output and changes neither; reading the two together is left to the reader, and they are never combined.
- **Validators.** Each adapter runs one pinned tool on the output, or on the output and its input, and writes one observation for one property, with the version the tool reports, its policy, exit code and raw output. A timeout, a crash or an output the adapter cannot read is `inconclusive`, never `valid`. The adapters are:

  | Analyzer | Property | Policy |
  | -------- | -------- | ------ |
  | `pyhanko` | `cms_signature` | Integrity and cryptographic validity of every embedded signature, with an empty trust store and no revocation lookup; an untrusted certificate does not change the verdict. pyHanko runs in its default strict syntax mode, which refuses to validate signatures in hybrid-reference files: that refusal, listed in the policy parameter `inconclusive_refusals`, is `inconclusive` unless another signature is `invalid`, with pyHanko's message in the summary |
  | `pdfsig` | `cms_signature` | Poppler's validation of every signature over its signed ranges, with `-nocert`; the verdict comes from the reported state, because `pdfsig` exits with 0 on a digest mismatch |
  | `openssl-cms` | `cms_signature` | Every dictionary with a `/ByteRange`, direct or indirect and including those in object streams and in the trailer, is listed from qpdf's JSON output. The gap of each range must be exactly a hexadecimal string (PDF whitespace allowed inside); its bytes must decode as CMS (DER or BER) and are verified with `openssl cms -verify -noverify` over the bytes the range covers. A gap that is not a hexadecimal string, bytes that do not decode as CMS, and exit code 4 are `invalid` |
  | `qpdf` | `structure` | `qpdf --check`; exit 0 is `valid`, 2 is `invalid`, 3 (warnings only) is `inconclusive` |
  | `cmp` | `input_preservation` | `cmp -n` over the byte size of the input: the output must start with every byte of the input, as an incremental update leaves them. Exit 0 is `valid`, 1 (a differing byte, or an output shorter than the input) is `invalid`, anything else is `inconclusive` |
  | `qpdf-prior-signatures` | `prior_signatures` | Every dictionary with a `/ByteRange` in the input, listed from qpdf's JSON output as for `openssl-cms`, must still be in the output with the same `/ByteRange` and `/Contents`; if a field of the input's `/AcroForm` had it as its value, a field of the same full name must still have it; and the bytes its range covers must be the same in both files. A signature that fails one of these is `broken` and makes the verdict `invalid`. An input without such a dictionary is `not_applicable`, unless qpdf had to recover the input, which is `inconclusive`. A range that extends past the end of the input, or a `/ByteRange` or `/Contents` that cannot be read, is `inconclusive` for that signature, because the input does not hold every byte it covers. A dictionary missing from an output that qpdf had to recover is `inconclusive`, and so is an input that qpdf had to recover even when every signature it listed is intact, because the recovery may have lost one. The bytes are compared by streaming their SHA-256, so neither file is held in memory |
  | `qpdf-byte-range` | `byte_range` | The signatures added by the implementation are the dictionaries with a `/ByteRange` that qpdf lists in the output and not in the input, compared by `/ByteRange` and `/Contents`; the details name the object and the field of each. Each range must start at byte 0 and end at the last byte of the output, and the bytes it leaves out must be exactly a hexadecimal string, PDF whitespace allowed inside, that decodes to the `/Contents` of the same dictionary. Bytes after the range or a gap holding anything else are `invalid`, and a `/Contents` that qpdf does not give as bytes is `inconclusive`. When qpdf had to recover the input, a signature that fails these checks is `inconclusive`, because it may be a signature of the input that the recovery lost. An output with no added signature is `invalid`, or `inconclusive` when qpdf had to recover it |

  The three last analyzers compare the output with its input, so they need both and have no baseline. Their verdict comes from exact byte comparisons over what qpdf parses, never from a scan of the file for PDF tokens. They answer apart from the `cms_signature` analyzers, which judge every signature of the output together: an output can keep every signature cryptographically valid and still be `invalid` for `cmp`, as JSignPdf's outputs of inputs with bytes before the header are. The gap is explained by its content, the signature's own `/Contents`, and not by the object offsets qpdf reports, because those are not corrected for bytes before the header.

  An output without any signature is `invalid` for the `cms_signature` adapters. pyHanko also exits with 1 for an intact signature with an untrusted certificate, so that exit code alone judges nothing: the verdict comes from the signature lines, and a failed validation without a line the adapter can read is `inconclusive`.
- **Implementations.** An adapter declares which scenarios it supports and builds the command line of an external process that reads the input and writes the output; the runner knows nothing else about it, so an implementation in any language is added without changing the runner. The runner copies the input into a fresh work directory and refuses it if its hash or size differs from the acquisition record, then runs the command with the limits described in `AGENTS.md`. A timeout is `timed_out`; a non-zero exit, a termination by signal, an exit 0 without an output file or an output that is not a regular file (such as a symbolic link) is `failed`, with the last 4 KiB of the process output in the error message and the credential password redacted from it. The output is copied and kept, under its SHA-256, only when the execution succeeded and the work directory was removed. Each run signs with a test certificate and RSA key generated for it, stored as a PKCS#12 outside the results and removed afterwards. A run selects its adapter by identifier. The adapters are:

  | Implementation | Revision | Supported scenarios | Command |
  | -------------- | -------- | ------------------- | ------- |
  | `pdf-signer` | Commit read from the installation | SHA-256, RSA PKCS#1 v1.5, `adbe.pkcs7.detached`, invisible, without timestamp or revocation information | `bin/signer-sign` with `--no-default-appearance` and `--no-default-timestamp`, and PHP's `memory_limit` disabled so that the runner's limit applies |
  | `jsignpdf` | Version read from the installed `jsignpdf-<version>.jar` | The same scenario, confirmed from signed outputs | `docker/jsignpdf-sign.php`, which calls `jsignpdf-php` with the OpenPDF engine, `-ha SHA256` and the library's default `-a`, and PHP's `memory_limit` disabled. `--overwrite` is never passed, so the signature is an incremental update. JSignPdf drops any bytes before the `%PDF-` header, so such an output does not start with all of the input's bytes: it starts with the input from that header on, and `cmp` reports it as `invalid`. The library's temporary files, `java.io.tmpdir` and `user.home` are in the attempt directory |
- **Compatibility of a revision.** An adapter may give a command that shows whether it applies to the installed revision, and the options its output must list, each under its own name and not inside a longer one, so `--cert` is not found in `--certification-level`. For `pdf-signer` it is `bin/signer-sign --help`, which must list every option the adapter passes: `getopt` ignores an unknown option, so a revision without `--no-default-timestamp` would sign with its default timestamp instead of failing. The command runs once per run, with the same isolation and limits as an attempt. A revision whose help does not list them, or whose help does not end with exit 0, is `incompatible`; it is still run, so every attempt records what happened and nothing is skipped. JSignPdf's adapter has no check.
- **Regression replay.** Every run replays the regression cases of `config/regressions/` and writes `regressions.json`. A case on a synthetic input regenerates the input with its generator, refuses it as `unavailable` with reason `hash_mismatch` when it differs from the case, and signs and validates it as an attempt of the run on the source `regression:<case-id>.pdf`; these attempts and their observations are kept in `regressions.json`, apart from the run's totals, because the cases are a failure-enriched selection. A case on an upstream input uses the attempt of the run on that input. Each case records the SHA-256 and size of its file and the status of its condition, checked by code registered for its id on the input and the output: `present` when the defect is in the output, `absent` when it is not, `undetermined` when the check could not read the output, and `not_evaluated` when there is no output to check, with the evidence in each case. A case of another scenario than the run, or on an input the run does not declare, has no attempt and is `not_evaluated` with that reason. A case without a condition check stops the run before signing.
- **JVM limits.** The JVM runs under the same limits as every other implementation, and the runner has no case for it: the address space bound of 1 GiB per process is what the run records as `address_space_bytes`. By default HotSpot reserves far more address space than it uses, and it does not start under that bound: the compressed class space alone reserves 1 GiB, and with default flags Temurin 21 needs 4 GiB. So the adapter reduces the reservations instead of raising the bound: `-Xmx512m`, `-XX:CompressedClassSpaceSize=64m`, `-XX:ReservedCodeCacheSize=48m`, `-XX:+UseSerialGC` so that the collector's reservations do not grow with the host's CPUs, and `MALLOC_ARENA_MAX=1`, because glibc reserves a 64 MiB arena per thread and the JVM does not start with these flags without it. `-XX:-UsePerfData` keeps the JVM from writing to `/tmp`. A document that needs more than this heap is a failed attempt. These settings affect speed, so the run records them in `implementation_runtime` and a performance comparison has to report them.
- **Comparison.** `bin/compare-runs` reads two finished run directories, a reference and a candidate, and refuses a directory without `run.json`, a record that does not follow its schema, an attempt of another run or scenario, two attempts on the same input, or an attempt without exactly one observation from each analyzer of its run. It pairs attempts by `source_id` and scenario. A pair is compared only when the input is available in both runs with the same SHA-256 and size; otherwise the input is reported as `only_in_reference`, `only_in_candidate`, `unavailable` (in either run) or `input_changed`, with no item, so nothing in it is counted as fixed, persistent or introduced. Runs without any paired input cannot be compared, for example runs of different scenarios. A paired input has one item for the capability, one for the execution outcome and one per analyzer present in both runs. A failure is what the summary of a run lists under its failures, decided by the same code: an execution that did not succeed, `not_run` included, unless it is a rejection that was expected; an expected rejection that succeeded; and a verdict of `invalid` or `inconclusive`. A succeeded execution that is not an expected rejection and a verdict of `valid` pass; a rejection that was expected, `not_evaluated` and `not_applicable` neither fail nor pass. An item is `persistent` when both runs fail it, `introduced` when only the candidate fails it, `fixed` when the reference fails it and the candidate passes it, `unchanged` when neither fails it and the values are equal, and `changed` otherwise. So an input that is no longer supported, an output that is now `inconclusive` and an expected rejection that now signs are introduced failures, while a capability change, a failure that became `not_applicable` or a rejection that was expected, and a verdict that went from `not_evaluated` to `valid` are changes, never fixes. Output hashes are not compared, because the certificate and the signature field name change on every run. `differences` states, without judging them, every difference between the runs in scenario, implementation and its runtime, analyzer revisions, the policies each analyzer recorded, source configuration, expected rejections, container image and resource limits; an analyzer present in one run only is listed there and has no item. The command writes `comparison.json` and its Markdown view `comparison.md` into a temporary directory next to the comparison directory, which must not exist yet, and renames it only when both are written, so an interrupted write never leaves a comparison directory behind. Regression cases are paired by id. A case present in one run only is `only_in_reference` or `only_in_candidate`, a case whose file has another SHA-256 or size in each run is `definition_changed`, because its condition may no longer mean the same, a case that either run did not replay is `not_replayed`, and a case whose input is unavailable or changed in either run is `unavailable` or `input_changed`; none of them has items. A paired case has one `condition` item, where `present` fails, `absent` passes and `undetermined` and `not_evaluated` neither fail nor pass, so the same rules give `introduced`, `fixed`, `persistent`, `changed` and `unchanged`; a case replayed on its own synthetic input also has the capability, execution and verdict items of its attempt. These items are totaled in `regression_changes`, apart from the inputs. `implementation_compatibility` is listed with the other differences. It exits with 1 when any item, of an input or of a regression case, is `introduced`, 0 when none is and 2 when the runs could not be compared. Which implementation is right when two runs differ is not decided here.
- **Differential comparison.** `bin/compare-implementations` reads two runs of one implementation and two runs of another, under the same checks as the comparison, and also reads `baselines.json`, refusing a baseline of another run, of an input the run did not attempt or of other content than the attempted input, or a second baseline from one analyzer on one input. It refuses runs that are not two per implementation, the same run given twice, two runs of one implementation at different revisions, the same implementation on both sides, a run without `baselines.json`, and runs that differ in scenario, source configuration, expected rejections, analyzers and their revisions, the policies of the observations and of the baselines, resource limits or the inputs they attempted; only the implementation, its runtime and the container image may differ, and each run records its own. A run of the comparison gives the denominator of every run, counted like the coverage of the report. An input is `paired` when it is available in all four runs with the same SHA-256 and size; otherwise it is `unavailable` or `input_changed` and has no item. A paired input has a capability item, an execution item and, only when all four attempts succeeded, one verdict item per analyzer, each with the value of the two runs of each implementation in order. An item with the same value in all four runs is an `agreement`, or a `shared_failure` when that value is a failure as the summary decides it; on an expected rejection, an execution that failed by rejecting the input and one that failed without rejecting it, such as an exit 0 without an output, are not the same value. Any other item is a difference and gets the first class that applies: `capability_mismatch` when the capabilities of the four attempts are not all the same; `unresolved_finding` when the two runs of one implementation gave different values, so the difference was not reproduced; `reproducible_implementation_defect`, on an input declared as an expected rejection, when one implementation rejected it in both runs and the other did not in both, whatever the input's baselines, because the declaration already says the input must be rejected; `expected_rejection` for any other difference on such an input, such as both implementations failing the declaration differently; `validator_disagreement`, for a verdict, when on one of the four outputs one analyzer of the same property fails and another judges it `valid`; `reproducible_implementation_defect` when one implementation fails the item in both runs and the other passes it in both, unless the input explains the failure; and `unresolved_finding` for anything else, such as both implementations failing with different values. The input explains a verdict that fails when that analyzer's baseline on the input is `invalid` or `inconclusive`, differs between the runs or is missing; an analyzer that compares the output with its input has no baseline, so its verdict is attributed by the comparison alone. It explains an execution that fails when any baseline of the input, from any analyzer in any run, is neither `valid` nor `not_applicable`, because an implementation may rightly refuse a damaged input. Such a difference is an `unresolved_finding` whose reason quotes the baseline. A defect names its `defective_side`, and every item cites the ids of the observations of a verdict and of the baselines it was judged against, while the input cites the four attempts. The totals count the items of each class, and the inputs whose items all agree or with at least one item of each other class. Disagreements between analyzers are never settled by vote, and agreement between the implementations does not establish conformance. Regression cases are not compared.
- **Report.** `bin/report` reads a finished run directory only: `run.json`, `attempts.json`, `observations.json` and `inputs.json`, under the same checks as the comparison. It refuses a run without `inputs.json`, a copy whose SHA-256 or size differs from the source configuration recorded in `run.json`, and a run whose attempts are not exactly one per declared input. Regression cases are not counted, because they are a failure-enriched selection of their own. Every table counts all the attempts of its rows, so its denominator shows the inputs that were unavailable (`not_evaluated`), `unsupported`, rejected as expected, not signed and signed; these five add up to the attempts. The coverage matrix has one row per stratum of the schema, a stratum without inputs included, and a last row for all inputs; because strata overlap, the rows do not add up to it. Each analyzer has its own table of verdicts by stratum, and analyzers of the same property that gave different verdicts on one attempt are listed side by side, never combined or settled by vote. A failure is decided by the same code as in the summary and the comparison, except that an unavailable input, which is never an implementation failure, is only counted in the denominator. Failures are grouped by cause, which is the outcome and the first line of the error for an execution, and the analyzer, verdict and first line of the evidence summary for an output. In an error, the paths under the runner's work directory `/sandbox/run-<hex>`, with or without escaped slashes, are replaced by `<work path>`, because they change on every attempt: JSignPdf's error carries its whole log, with the path of the input. In a summary, the field names and object references that the analyzer lists in `evidence.details.signatures` are replaced by `<signature>`, because an added signature's field name changes on every output and an analyzer names a signature without a field by its object. Each cause is shown whole, as it is compared, because a cut cell can hide what tells two causes apart: JSignPdf's errors share a long log preamble before the exception. They are also grouped by input source. A report of a `failure_enriched` sample says that none of its counts is a compatibility rate, and one of a `stratified` sample that a share holds for one stratum of its pool only.
- **Regression case.** A case names the GitHub issue it comes from, the scenario it runs under, the condition that shows the defect and one of the two input forms allowed by `CONTRIBUTING.md`: a synthetic input, identified by the generator under `tests/Fixtures/Synthetic/` that writes it and by the SHA-256 and byte size it must have, or an upstream input, identified by the `source_id` of an input declared in `config/inputs.json`, whose hash is already recorded there.
- **Metric.** Either `{"status": "available", "value": ...}` or `{"status": "unavailable", "reason": ...}`. An unavailable metric has no value, so it cannot be mistaken for zero.
